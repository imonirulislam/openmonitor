# Security Policy

## Reporting a vulnerability

**Please do not open a public issue for security problems.**

Report privately through GitHub's [private vulnerability reporting](https://docs.github.com/en/code-security/security-advisories/guidance-on-reporting-and-writing-information-about-vulnerabilities/privately-reporting-a-security-vulnerability):
go to the **Security** tab of this repository and choose **Report a vulnerability**.

Please include:

- What the issue is and roughly how severe you think it is
- Steps to reproduce, or a proof of concept
- The commit or version you tested against
- Any deployment specifics that matter (self-hosted vs. managed Postgres, reverse proxy, etc.)

You will get an acknowledgement as soon as the maintainer sees it. This is a small
project maintained by one person, so please allow reasonable time for a fix before
disclosing publicly.

## Supported versions

OpenMonitor is pre-1.0. Only the latest commit on `main` receives security fixes.
There are no maintained release branches yet.

## Insecure-by-default values you must change before deploying

The defaults in `.env.example` and `docker-compose.yml` exist to make local development
work with zero configuration. **Every one of these is unsafe in a real deployment:**

| Value | Default | Why it matters |
|---|---|---|
| Seeded admin | `admin@openmonitor.local` / `changeme` | Full admin login. Created by `bun run db:seed`. |
| `AUTH_SECRET` | `change-me-to-a-32-byte-random-secret` | Signs session cookies. A known value means forgeable sessions. |
| `PROBE_API_KEY` | `change-me-probe-key` | Bearer token for probe ingestion. A known value lets anyone write fake probe results. |
| Postgres credentials | `openmonitor` / `openmonitor` | Compose-only, but do not reuse them. |

Generate a real `AUTH_SECRET` with `openssl rand -base64 32`.

The demo seed is deliberately **not** part of `docker compose up` — it sits behind a
profile (`docker compose --profile seed up seed`) so a production stack never creates the
known-password admin user. If you ran the seed anywhere reachable, change that password.

## Security-relevant design notes

- **Roles are `admin` > `editor` > `viewer`.** Server actions call `requireEditor()`;
  `requireAdmin()` guards admin-only screens.
- **Admin writes go through `apps/web` server actions**, not `apps/api`. `apps/api`
  exposes public reads plus bearer-authenticated probe ingestion only. Adding an
  authenticated write endpoint to `apps/api` is a security-relevant design change.
- **`apps/status-page` never touches the database.** It talks to `apps/api` only, which
  keeps the public surface free of database credentials.
- **User input is validated with Zod at the boundary** (forms and request bodies).
- **Status pages can be password-protected**; unlock tokens are handled in
  `apps/api/src/routes/unlock.ts`.
- **Inbound Slack webhooks** are verified in `apps/api/src/lib/slack-signature.ts`.

## Out of scope

- Findings that require an already-compromised host or database
- Missing hardening on the local `docker-compose.yml`, which is explicitly a development
  setup and is documented as such
- Reports generated by automated scanners with no demonstrated impact
